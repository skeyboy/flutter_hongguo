# 网络请求慢：实测与修复方案

本机实测主要耗时来自“上游快速返回空响应 + 客户端长退避等待”，不是签名计算。先优化内容请求的恢复策略，再补取消、去重和缓存；播放起播耗时需要单独测量下载与解密，不能直接当作 API 慢。

## 测量范围与证据

- 日期：2026-10-21；macOS 当前网络；代码以已发布 v0.2.9 / `6c6e196` 的网络实现为基准。
- 独立匿名客户端，列表签名开启，单次阶段超时设为 10 秒，使用现有默认 1/2/4 秒退避；顺序执行 3 轮题材和列表，以及一次详情和播放元数据。
- 不读取本机登录态或已保存设置，不下载媒体，不记录完整 URL、请求头、签名、密钥或响应正文。
- [脱敏原始计时](../evidence/network-latency/2026-10-21-macos.json)。Dio 请求耗时包含该请求传输/转换；操作总耗时还包含限速排队、签名和重试等待。本次不是 DNS/TCP/TLS 分阶段 API 抓包，也不是多设备统计。

| --- | ---: | --- | --- |
| 题材第 1 次 | 3743 ms | 空 203 ms、空 85 ms、有效 400 ms | 3 次请求，等待 1+2 秒 |

## Evidence → Finding → Path

| 证据 | 结论 | 修复路径 |
| --- | --- | --- |
| E1：原始计时中，已签名列表仍出现 HTTP 200 / 0 字节 | 签名默认开启已解决不了所有空响应；不能把所有空响应定性为缺签名。上游空响应原因尚未证明 | 按错误类型恢复，有限快速重试；失败保留缓存，不持续请求 |
| E2：`packages/api/lib/src/network_retry.dart` 默认 1/2/4 秒；`catalog.dart` 重试全部 CatalogError、FormatException 和瞬态传输错误 | 快速失败也被拉长到 7 秒；业务拒绝、错误结构等可能被无效重复请求 | 分离空响应、网络瞬态、限流与确定性业务错误；限定总时间预算 |
| E3：`AppSettings.timeoutSeconds=60`，Catalog API 与官网分别调用同一重试器 | 慢网会累积多次超时，且详情要等 API 重试耗尽才回退 | 元数据专用超时，详情主链路与回退共享 deadline；媒体下载保持独立配置 |
| E4：`library_page.dart` 有 250 ms 合并与 revision 校验，但 CatalogRepository 无取消参数 | 旧请求结果不会覆盖新页面，但旧请求、排队和重试仍占资源 | 可取消请求作用域；排队、退避、发送和页面销毁都响应取消 |
| E5：`_reload` 每次异步启动 `_loadThemes`；主题未持久缓存，CatalogClient 无列表/主题 in-flight 去重 | 反复进入分类、刷新或多个调用者可能制造重复请求 | 题材按 genre 缓存；同 key 合并在途请求；订阅释放不误取消其他调用者 |
| E6：现有 LibraryCache 已先显示快照，但随后每次联网刷新，缺少短期 freshness 判断 | 已有缓存策略值得保留；短时间回看仍会重复消耗网络 | 新鲜缓存短期直接复用；过期缓存 SWR；显式刷新可以绕过 freshness |
| E7：MediaCache 完整下载、解密、校验后才返回 source，播放器等待 active.source | 起播等待还可能是整集准备，不能全部算作网络 API 耗时 | 分段记录解析/下载/解密/校验/打开；优先播放已缓存下一集 |

现有保护应保留：请求启动间隔 260 ms（仅串行启动，慢请求不会锁住全部响应）；首页题材与列表已并行启动，不应再作为“串行两次”的修复；MediaCache 已有前台优先及后台并发预留；解密和校验已在 Isolate，不能建议重复迁移。

默认 60 秒下，单纯每次都触发一个接收超时，4 次请求约 247 秒；详情若 API 和官网两段都如此，约 494 秒。这里只是单阶段超时的算例，**不是实测，也不是严格总上限**：连接、发送、接收和排队还会叠加，接收超时也不是完整业务操作的总 deadline。

## 分阶段修复设计

### 第一阶段：减少无效等待

1. 给元数据引入独立策略，建议连接 4–5 秒、接收 8–10 秒、整体预算 10–15 秒；数值需以真实移动网络数据调整。使用单调时钟计算剩余预算，等待、排队与每次发送前均检查；超预算真正取消 Dio 请求，不能只对 Future.timeout 后留下后台工作。
2. HTTP 200 空体或缺失必要字段：与网络超时区分；最多 2 次恢复尝试，建议 300–500 ms、800–1000 ms 抖动，且服从现有 260 ms 启动间隔及共享预算。通过注入时钟/等待器做确定性测试。不得无限加速重试；上游要求等待时优先尊重该要求。
3. 网络瞬态失败：交互请求优先仅重试 1 次；429 遵守 Retry-After，超过交互预算时结束本轮并展示缓存/可重试状态，不在后台立即重发。禁止静默截断服务端要求的等待时间后提前请求。
4. 明确的业务拒绝、参数错误及确认不兼容的协议结构不盲重试。未知空响应不展示为“没有内容”，也不覆盖已有有效缓存。
5. `detail` 主 API 预算结束后快速进入官网回退，二者共享总预算；只在确认主接口不可用时使用短期失败冷却，避免把一次空响应当永久故障。网站回退失败仍保留已知分集与手动重试入口。

这一阶段目标是缩短恢复等待并及时反馈，不保证消除上游空响应，也不能承诺更短重试一定提高成功率；需要同时比较成功率和延迟。

### 第二阶段：减少重复请求

- 对列表/搜索/榜单按完整请求键合并在途请求，键包括协议/身份作用域、genre/sort/theme/query、cursor、seen 等实际影响响应的参数。凭据变化清空对应缓存；不记录原始凭据作为可见 key。
- 题材缓存建议 6 小时；同请求列表新鲜期建议 30–60 秒。新鲜期不重复刷新；过期缓存立即展示，再执行一次刷新；手动刷新强制重新验证。
- 给 CatalogRepository 设计通用取消上下文，不把 Dio 类型泄漏到 Flutter 视图。取消只在最后一个共享订阅者离开时传递至底层，避免新页面的共享请求被旧页面取消。
- 快速筛选继续保留 250 ms 合并；旧 generation 的排队、退避和在途调用均停止。取消不触发网络错误提示或自动重试。
- 首页列表请求优先于非关键题材刷新；维持限速，避免通过删除 260 ms 保护来“提速”。先显示已有筛选项及缓存，不让筛选元数据阻塞列表。

### 第三阶段：分离起播与下载体验

- 日志增加逻辑请求 ID、attempt、queueMs、signMs、transportMs、backoffMs、cacheHit、错误分类；不得记录 URL 参数、签名头、媒体密钥或会话。
- 另记录播放器解析、下载字节/速度、解密、校验、打开到首帧的耗时；带宽不足时降低自动清晰度，并保证前台任务优先于预缓存。
- 保留“本地普通 MP4 → 播放器”架构，先优化已缓存命中与下一集预准备。边下边播涉及 CENC 分段解密、索引完整性、Range 和损坏恢复，应单独立项验证，不能作为简单网络修复直接替换。
- PC、Android、iOS 共用请求策略；移动端增加断网/蜂窝/Wi-Fi 切换验证，后台任务按系统约束恢复，不用无限重试替代系统调度。

## 验证与验收

1. 单元测试：空响应后成功、持续空响应、非重试业务错误、429/Retry-After、总预算、取消排队/退避/发送、去重与多订阅取消隔离。
2. Widget 测试：缓存立即可见、刷新失败保留内容、切换筛选停止旧任务、旧结果不覆盖当前条件、题材失败不阻塞列表。
3. 集成测试：macOS 正常与弱网；Android 真机及 iOS 模拟器分别验证生命周期和网络切换。此次匿名 Mac 探测不能代表移动设备真实质量。
4. 对比至少 30 个样本的成功率、空响应率、请求数、P50/P95 和首屏时间，分冷缓存、热缓存、无网、弱网场景；不要把本次 3 轮探测当作统计结论。建议以缓存可见 <100 ms、快速空响应恢复不再固定消耗 7 秒、操作按总预算结束为验收目标，指标为待验证目标。

分析阶段只新增文档、证据与诊断工具；随后已按用户要求实施下述修改。


## 实施与验证结果

已落实前三阶段的请求恢复、12 秒总预算、实际传输取消、在途共享与订阅隔离、6 小时题材缓存、30 秒列表新鲜期、强制刷新，以及媒体准备和播放器打开的独立计时。[实现设计与源码定位](../design/catalog-network-performance.md)。未改为边下边播。

### 上游复测

- [短恢复后的连续空响应样本](../evidence/network-latency/2026-10-21-macos-after-empty.json)：两次列表失败分别 1611ms、1821ms，每次 3 个请求；相较初次测量的 7468ms，不再固定等待 7 秒。两次测量的网络/上游条件并不相同，只能证明恢复等待缩短，不能作为成功率对照。
- [最终诊断样本（含分段计时）](../evidence/network-latency/2026-10-21-macos-after.json)：3 次列表分别 445/448/521ms，均为单次请求；题材首次空响应恢复后 2194ms 成功，后两次命中内存缓存（无网络请求、毫秒取整显示 0）；详情 708ms、播放元数据 573ms，均含两次请求。
- 样本少、上游仍会空响应。上述数字不是性能承诺；持续故障时保留已有有效缓存，初次无缓存则及时显示可重试错误。
